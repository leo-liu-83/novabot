# 安全与权限

NovaBot 把能力拆成几条独立边界：身份、执行档位、技能放行、网络访问、MCP 授权和确认门。任何一条都不能替代其他条。

## 1. 身份与天花板

| 身份 | 执行天花板 | 默认档位 |
|---|---|---|
| 多用户匿名 | T1 | T0 |
| 普通用户（未授权） | T1 | T0 |
| 普通用户（管理员授权 T3） | T3 | T0（需自己提） |
| 管理员 | T4（受服务封顶） | T3 |
| 单用户机主 | T4 | T1 |

- 管理员用 `/exec-limit` 调整非 admin 账号的天花板
- 天花板只限制“最高能到哪”，不会自动把当前档位提上去
- `/exec` 只能在天花板内调整，且只对当前会话生效

## 2. 执行档位

| 档位 | 能做什么 |
|---|---|
| T0 | 不执行任何命令 |
| T1 | 只运行已放行技能 `scripts/` 下的 `.py` |
| T2 | 工作区内单条只读命令（`ls`/`cat`/`grep` 等） |
| T3 | 任意 shell，每条命令确认 |
| T4 | 任意 shell，免确认 |

不可覆盖的底线：

- 硬黑名单：破坏性删除、fork bomb、磁盘写入、格式化、关机重启等
- 命令按控制符切段检查，`ls && rm -rf /` 也会被拦
- T2 的路径参数必须落在工作区内
- 任何档位都不能突破身份天花板

## 3. 技能审查

- 系统层技能只读，始终加载
- 共享层和私有层需要审查
- 脚本技能默认不放行；未放行不加载
- 纯提示词技能默认加载，但可被拒绝
- 放行绑定内容哈希；内容变化后需要重新扫描
- 管理员可放行危险技能；普通用户只能放行安全技能
- 拒绝操作只有管理员 / 单用户机主可用

扫描是**咨询性**的：

- 会检查提示词注入、隐藏字符、危险脚本模式、凭据路径等
- 混淆载荷（如 base64）静态分析看不见
- `No findings` 不等于安全

## 4. 文件与技能门

- 文件工具和只读命令会拦截未放行技能的目录
- 保证的是“未放行技能正文不能被直接点名读取”
- `grep -r "x" .` 这类递归扫描仍可能遍历到工作区内容；彻底隔离需要 OS 级沙箱，本版本不做

项目会话的边界（详见 [功能说明](features.md#13-项目project)）：

- 工作根是项目目录，读写在该目录内直接放行；项目外路径与敏感文件走确认
- T4 在项目会话里收窄为"项目内免确认"：点名项目外路径的命令仍会要求确认
- 项目里的 `AGENTS.md` 与 `.novabot/notes/*.md` 是**项目作者的内容**，会进入模型上下文，等于把这段文字当指令；不可信项目应先读一遍
- 确认卡的"总是允许"按具体路径记忆，且只在当前会话内有效，换会话重新确认

## 5. 网络搜索与抓取

### 抓取确认

`web.fetch.permission`：

| 值 | 行为 |
|---|---|
| `ask` | 每个 URL 确认；allowlist 域名免确认 |
| `allow` | 所有公网地址免确认 |
| `deny` | 不注册 webfetch 工具 |

`url_allowlist` 是免确认名单，不是硬白名单。`allow` 模式下所有公网地址都可抓取。

### SSRF

抓取会拒绝：

- localhost / 回环
- 内网 / 私网
- 链路本地和云元数据地址
- 保留地址

每一跳重定向都会重新校验。配置期不解析 DNS，因此仍存在 DNS rebinding 时间窗。

### 内容注入

搜索结果和抓取页面会按不可信外部内容包装；伪造边界标记会被改写。疑似注入只记录日志，不自动阻断。

## 6. MCP

- 系统层 server 随发行版配置，默认启动
- 用户层 server 默认关闭，需要管理员开放账号 MCP 能力
- server 级审批模式：`ask` / `allow` / `deny`
- 单个工具可覆盖 server 模式
- `allow` 是用户显式决定；MCP 的只读声明不可作为安全依据
- `ask` 调用会显示参数并等待确认
- 每个用户可连接 server 数量有上限

## 7. 数据与密钥

- 模型 key、搜索 provider key 和 MCP header 明文保存在本机
- TUI 登录 token 明文保存在 `data/login.json`（`remember_login=false` 时不写）
- 数据库文件权限就是主要边界
- 不要把 `~/.novabot/` 提交到版本库或公开分享
- 删除账号会清理会话、附件和相关数据；仍然建议定期备份

## 8. 部署建议

- 单用户模式默认 API 不鉴权，**不要把 `--host 0.0.0.0` 直接暴露到公网**
- 多用户模式先在本机 TUI 创建管理员，再开放端口
- 反向代理需要保留原始 `Host` 头，并考虑额外鉴权
- 高风险技能、MCP server 和 shell 工具请只在可信环境启用
- 定期检查 `/exec-limit`、搜索配额和 MCP 授权

## 9. 已知风险

- 同机所有账号在 OS 层是同一个用户，不提供进程级隔离
- 技能扫描无法识别所有混淆载荷
- `grep -r` 可以绕过“点名读取”的技能门
- DNS rebinding、TOCTOU 等时间窗未完全消除
- Web 与 TUI 的中文输入法兼容性依赖终端
- 项目由模型生成，使用前应自行审计
